What each feature costs in flash

Every subsystem is a cargo build option of mmc-drive (session 42). The base build, with none of them, already carries FOC, the flux observer and sensorless start, HFI, hall FOC, the R/L probe and the host link: 48.5 KB on the F302, 47.7 KB on the G474, 52.0 KB on the H743. What each mode costs in interrupt time

Measured on the F302 at 72 MHz, where a 10 kHz control tick has 7,200 cycles. Each figure is the worst tick over about 3.5 s of steady running in that mode, read from the firmware's own cycle counter without stopping the core. The shipped build has hall position but no six-step, estimator or cogging feed-forward; the all-features build adds those three.

Optimizations

In place

  • Per-board feature sets. The F302 builds the link and hall position only: 49.5 KB, 14.0 KB free (was 1.8 KB, under the CI floor).
  • HFI shadow made opt-in. Hall FOC on the F302 went from 5,016 to 3,861 cycles a tick.
  • opt-level 2, fat LTO, one codegen unit for everything the control interrupt reaches; "s" for boot, executor, link and protocol code on the F302 (session 38).
  • Hardware square root, nibble-table CRCs, 32-bit telemetry period (session 38): about 3.1 KB off the F302 image.
  • Out-of-line rarely run HFI code (Tracker::update, the observer hand-back): about 280 B (session 41).
  • Pinned compiler (rustc 1.99.0) and a CI size check per board, so a toolchain update cannot silently cost flash.

Tried and rejected

  • Whole F302 image at opt-level "s". Saves 9.2 KB, but HFI at 20 rad/s el then takes 7,231 cycles, over the 7,200 budget.
  • mmc-core alone at "s". Gains 0.3 KB; not worth a slower Foc::step.
  • Moving the HFI amplitude schedule out of line. Cost 72 B more than leaving it inline.
  • Removing the friction feed-forward alone. 72 B; not worth a parameter change.

Found while measuring

The quiet HFI default switched on the shadow in every hall FOC drive

Session 42 made hfi_v 0.3 the saved default for sensorless starts. HFI also ran in shadow under hall FOC whenever hfi_v was above zero, costing 1,160 cycles a tick, and in an all-features build it overran the interrupt. The shadow is now the opt-in build feature hfi-shadow, and hfi_v only controls the sensorless start.

Reading memory with probe-rs pauses the core

The first profiling pass cleared and read the cycle counter with probe-rs read/write. With the bridge switching at 600 rad/s el, that momentary halt froze the PWM and tripped the overcurrent limit. The profiler now uses OpenOCD's memory access port, which does not halt; every run in the final pass stayed healthy. Earlier sessions' "while running" reads used probe-rs at low speed only.

All features plus fixq does not fit the F302

The full set is 61.9 KB, 1.6 KB free and under the 2 KB CI floor; adding the integer HFI path overflows the 62 KB region. The shipped set plus fixq fits (56.2 KB).

STM32H743 build test

A new crate, mmc-fw-h743, builds the full application for an STM32H743ZI (Nucleo-H743ZI: Cortex-M7 at 480 MHz, 2 MB flash, 1 MB RAM) with embassy-stm32: every drive feature, the host link on USART3 with DMA, the 480 MHz clock tree, and the full 32 KB saliency-sweep buffer the F302 cannot hold. The power stage is a stub. Currents read zero, duties are dropped, the tick runs from an executor ticker rather than an ADC interrupt, and parameters live in RAM. It shows what the application costs on the part, and it is the starting point for a real port.

What a real H7 port needs

  • TIM1 (or HRTIM) centre-aligned PWM with dead time and break, triggering injected conversions on ADC1/2; Engine::tick in that interrupt.
  • A flash parameter store: the H7 erases 128 KB sectors, so the table needs a sector of its own, or the backup SRAM.
  • Cache care: DMA buffers (serial ring, burst) in non-cacheable RAM or with cache maintenance; the tick and its data in ITCM/DTCM for deterministic timing.
  • A DeviceKind for the protocol (the skeleton reports Unknown(4)).

What the headroom would buy

  • A faster loop, with a higher HFI carrier as a result: at 40 kHz control the ++−− carrier sits at 10 kHz, past most of the whine motor 3 makes at 2.5 kHz.
  • Every feature at once, with the HFI shadow, the estimator and cogging FF together and room left over.
  • Double precision for the estimator and the online fits, if wanted (the M7's FPU has it; the M4F's does not).

How these numbers were taken

Memory

  • tools/feature_sizes.sh <crate> builds each feature set and reads sections with llvm-size; flash is the programmed binary (.data initial values included).
  • The firmware crates pass every feature through, so --no-default-features --features … builds any set.
  • G0B1: protocol-only firmware (no inverter), 14,920 B flash, 2,312 B RAM.

Interrupt time

  • F302: tools/isr_profile.sh starts a drive, clears isr_max_cycles after it settles, and reads it 3.5 s later through OpenOCD without halting. Each row also records the drive's state sequence, so a faulted run shows as one.
  • G474: same Cortex-M4 code as the F302, so the F302 cycle counts are used, against its 8,500-cycle budget (170 MHz, 20 kHz). Not measured: the G474 bench is not connected.
  • H743: the M4 cycle counts scaled by 0.55–0.8 for the M7. An assumption, to be replaced by a measurement on hardware.
  • Cortex-M0+: the integer HFI step run in an instruction emulator with M0+ cycle costs (tools/m0_cycles.py, session 40).
